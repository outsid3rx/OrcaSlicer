# Состав и выпуск комплекта

[English](DISTRIBUTION.md) | [Русский](DISTRIBUTION.ru.md)

Слайсер, MCP и навык хранятся в одном форке [outsid3rx/OrcaSlicer](https://github.com/outsid3rx/OrcaSlicer). Репозиторий не использует отдельный checkout/submodule для MCP и не требует backend для библиотеки рецептов.

| Каталог | Ответственность |
|---|---|
| `src/slic3r/AgentControl/` | Нативные операции с текущим GUI-проектом, проверка параметров, задания и управление печатью |
| `mcp/` | Python stdio MCP, выбор окна, адаптация ответов, локальные рецепты |
| `skills/orca-mcp-control/` | Единственный исходник инструкций рабочего процесса агента |
| `scripts/agent/` | Установка, настройка клиентов и упаковка комплекта |
| `.github/workflows/agent_mcp.yml` | Проверки MCP и установщика отдельно от CMake-сборки |
| `.github/workflows/agent_release.yml` | Сборка набора файлов релиза из проверенного нативного артефакта |

Каталоги MCP и навыка отделены от исходников upstream. Нативный модуль использует ограниченные точки интеграции в Orca. Обычная CMake-сборка не устанавливает Python и не запускает MCP. Обновление upstream требует проверки этих точек интеграции и нативных тестов; отдельная папка не устраняет конфликты автоматически.

## Версии и артефакты

Релизы форка имеют вид `<версия upstream>-agent.<ревизия>`, Git-теги начинаются с `v`: например `v2.5.0-dev-agent.1`, затем `v2.5.0-dev-agent.2`. После перехода на upstream 2.5.1 — `v2.5.1-agent.1`. В `agent-release.toml` хранятся положительный номер ревизии форка и полный SHA выбранного upstream commit. Упаковщик читает версию из неизменённого `version.inc`, проверяет, что выбранный commit входит в историю релиза и содержит ту же версию, и записывает обе идентичности в манифест. About/API приложения сохраняет версию upstream; версия выпуска форка отражается в теге, именах артефактов и манифесте.

MCP, wire protocol/API revision и формат рецептов версионируются независимо. MCP 0.4.0 может входить в форк 2.5.0-dev-agent.1. Запущенная Orca сообщает поддержанные методы и схемы; номер релиза не заменяет эту проверку.

Релиз содержит нативный DMG, wheel/sdist MCP, ZIP навыка и установочный архив. `release-manifest.json` связывает комплект с исходниками и версиями; `SHA256SUMS` позволяет проверить целостность файлов. Контрольная сумма не заменяет проверку происхождения, подписи приложения или нотариального статуса.

`agent_release.yml` запускается вручную. Укажите ID успешного `Build all` из того же репозитория на том же commit и точное имя артефакта с одним DMG. Workflow сверяет происхождение, проверяет DMG, штатный CA и зависимости, выполняет тесты и собирает архивы. По умолчанию результат остаётся артефактом Actions.

Для создания **draft** запустите workflow на существующем теге `v<версия upstream>-agent.<ревизия>` с `create_draft=true`. Отдельного действия публикации workflow не выполняет. Исходники в состоянии dirty допускаются только для локального тестового комплекта, отмечаются `publishable=false` и не проходят `--require-clean`. Чистый комплект включает архив соответствующих исходников.

Локальная проверка и упаковка на macOS из корня checkout:

```sh
uv run --no-project --python 3.12 scripts/agent/verify_dmg.py --dmg /absolute/path/OrcaSlicer.dmg \
  --output /absolute/path/native-verification.json --source-commit "$(git rev-parse HEAD)"
uv run --no-project --python 3.12 scripts/agent/package_release.py --dmg /absolute/path/OrcaSlicer.dmg \
  --native-report /absolute/path/native-verification.json \
  --output /absolute/path/new-empty-release-directory --require-clean
```

Проверка DMG фиксирует целостность, платформу, наличие AgentControl, зависимости, CA и статус подписи. Она не запускает приложение и не доказывает работу API, AMS или физической печати; `runtime_tested=false` сохраняет эту границу. Проверка не подтверждает notarization.

GitHub workflow при явном выборе подготавливает **draft**. Публикация, подпись Developer ID и notarization не возникают из наличия workflow: опубликованные статусы и поддержанные платформы указываются в конкретном релизе. Первая локально проверенная платформа — macOS arm64; исходники для других платформ не являются свидетельством успешной установки или работы на них.

## Установка и обновление

Установщик MCP использует отдельное окружение `uv tool install` и постоянный абсолютный путь команды. Клиенты не зависят от checkout после установки. При выборе Codex/ZCode через `--client` навык копируется из единственного исходника в их каталоги. Резервные копии конфигураций сохраняются рядом с изменяемыми файлами; сторонние MCP-записи остаются на месте.

Сервер stdio можно использовать с Codex, Claude Desktop, Cursor, Windsurf и ZCode в зависимости от возможностей клиента. Запуск установщика без `--client` выдаёт универсальную конфигурацию. Необязательные `--client codex` и `--client zcode` автоматизируют настройку этих клиентов и установку навыка. Текущий установщик рассчитан только на macOS.

Без `--client` установка настраивает только MCP-сервер и печатает его конфигурацию stdio; навык автоматически не устанавливается. Для других клиентов перенесите включённый в комплект каталог `skills/orca-mcp-control/` по инструкции установки навыков вашего клиента. Если клиент не поддерживает навыки, примените инструкции из `SKILL.md` как руководство проекта.

Приложение устанавливается/заменяется отдельно из DMG. Установщик MCP не изменяет `/Applications`, Keychain, профили Orca или TLS-доверие. Управление и печать включаются владельцем через окружение Orca; настройка клиента не включает их скрыто.

Для сборок с `SLIC3R_AGENT_CONTROL=ON` используется ручной канал обновления через Releases форка: автоматическая проверка upstream выключена, ручная команда открывает страницу форка. Установка официальной сборки upstream заменит приложение версией без AgentControl. Поведение штатной проверки обновлений конкретного установленного приложения зависит от его сборки: старые сборки не следует считать переключёнными на канал форка только после обновления MCP.

SQLite рецептов, операционные квитанции и native print journals находятся вне установки. Удаление Python-пакета не удаляет их. Дамп рецептов не содержит квитанций, поэтому не подходит для восстановления состояния незавершённой операции.

## Публичный и локальный состав

В артефакты не включаются `.venv`, auth descriptors/tokens, SQLite-база, пользовательские модели, личный CA Bambuddy или локальные рабочие сборки. Публичная Orca использует штатный набор сертификатов upstream. Сертификат, который пользователь вручную добавил в ресурсы `.app`, не становится частью публичного релиза и может потеряться при замене приложения; автоматический перенос такого доверия не обещается.

AGPL-лицензия и соответствующие исходники доступны вместе с комплектом. Оригинальная атрибуция OrcaSlicer и его предшественников сохранена в [upstream README](UPSTREAM_README.md).

## Обновление из upstream

Изменения форка остаются в `main`; выбранный upstream commit добавляется merge без переписывания опубликованной истории:

```sh
git fetch upstream
git merge <reviewed-upstream-commit>
```

Разрешите конфликты и запишите точный upstream SHA в `agent-release.toml`. При смене версии upstream начните `fork_revision` с 1; иначе увеличьте номер для следующего релиза форка, включая обновления между dev-коммитами с одинаковой версией. Опубликованный тег не используется повторно. Перед релизом изучите изменения и повторите нативные/MCP тесты и сборку. Упаковщик проверяет историю и совпадение версий, но не оценивает полноту ревью upstream. Версия MCP меняется при изменении его пакета; совместимость нативного API и рецептов проверяется отдельно. Фоновые merge и автоматическая публикация релизов не включены.
