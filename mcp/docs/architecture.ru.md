# Устройство адаптера

[English](./architecture.md) | [Русский](./architecture.ru.md)

Отдельный Python-процесс преобразует явно включённый нативный API агента Orca в универсальный MCP stdio. Официальный MCP SDK отвечает за инициализацию, кадрирование, схемы инструментов и жизненный цикл. Версия протокола остаётся v1; ревизия API 3 расширяет выбор устройств, инвентарь AMS, предпросмотр нарезки и отчёты печати. Исходные десять специализированных инструментов совместимы. Ещё пятнадцать групп нативных инструментов открывают фиксированные наборы действий для редактирования, файлов, предпросмотра, истории, пакетов, пресетов и принтеров. Три инструмента рецептов управляют локальным хранилищем и защищённым нативным применением. Инструмента произвольного вызова нативных методов или выполнения кода нет.

```text
MCP stdio client
  -> server.py: 28 tools, selectors, image conversion, outcome semantics
  -> client.py: private discovery, explicit target, HTTP RPC, bounded observation
  -> authenticated loopback native queue
  -> GUI controller and native scene/settings/geometry/printing domains
```

Адаптер не запускает Orca и не включает его неявно. Удалённый HTTP-транспорт MCP находится за пределами локального адаптера. Нативные схемы параметров и проверки остаются авторитетными, включая наследование настроек и ограничения возможностей конкретной сборки.

## Идентичность и файлы

Каждая операция выбирает полную пару UUID сессии/окна; подписи, фокус, PID и порядок списка не могут выбирать цель. Нативные ответы должны отражать ту же пару. Токены остаются в клиенте и скрываются в результатах. Дескрипторы проверяются по уже открытому файлу: владелец/режим в POSIX, владелец/защищённый DACL через pywin32 в Windows. Неуспешная или недоступная проверка отклоняет файл. Прокси и перенаправления отключены. До отправки действуют ограничения дескриптора и полезной нагрузки.

Корневые каталоги файлов принадлежат окружению запуска нативного приложения, заданному владельцем. Нативная конечная точка проверяет фактически открытые входные файлы и делает приватные снимки; экспорт сначала готовится во временном месте, затем публикуется атомарно. MCP передаёт явные локальные пути, но не может расширять разрешённые корни. Обычное изменение настроек и пресетов исключает скрипты и учётные данные.

## Изменения и задания

Каждому изменению нужны исходный токен состояния и явный ID запроса. Адаптер проверяет сочетания селекторов, но не дублирует нативную проверку настроек/геометрии. После структурных изменений нужно обновлять идентификаторы сцены и ревизии сетки. Смешанные группы изменений консервативно объявляют разрушительные возможности; группы принтеров объявляют влияние на внешний мир.

Наблюдение ограничено и никогда не отправляет операцию повторно. При потере ответа о приёме для изменения даётся консервативная рекомендация повторить только точные исходные аргументы и ID. Для восстановления неизвестные нативные методы считаются изменениями. Когда известен ID задания, следует наблюдать его. Срок хранения нативных результатов ограничен; у адаптера нет постоянного кеша выполнения ровно один раз. У отмены собственная квитанция, которая не означает остановки физического принтера.

Нативные PNG преобразуются в изображения MCP без второй base64-копии в структурированном JSON. Некорректные или слишком большие ответы предпросмотра отклоняются.

## Результаты печати

Подготовка фиксирует приватный артефакт, состояние, конечную точку, параметры и срок действия; ничего не загружает. Отправка требует включения владельцем нативного доступа и ID предупреждений. Нативный журнал долговечно расходует операцию до передачи по сети. Неизвестные результаты сверяются, а не отправляются автоматически повторно. Нативный успех может означать принятую загрузку или принятое задание и не доказывает физическую печать. Команды управления явно влияют на всю конечную точку.

Адаптер анализирует только известные долговечные оболочки квитанций. Отсутствующий, некорректный или неизвестный результат сохраняет исходную квитанцию, добавляет `outcome_uncertain=true`, устанавливает `isError=true` и предлагает сверить ту же операцию. Флаг ошибки никогда не разрешает новый ID отправки или повтор. Известная использованная квитанция — наблюдение предыдущей попытки, а не доказательство второй передачи.

## Границы проверки

Модульные тесты и stdio-фикстуры официального SDK покрывают идентичность, валидацию, восстановление, обработку изображений, аннотации и долговечную семантику результатов. Выполненные нативные проверки macOS arm64 покрывают реальное поведение редактора и загрузки на локальный приёмник, включая потерю ответа после принятия файла. Физическая BBL-печать и выполнение в Windows/Linux требуют отдельных проверок. Подробности и даты приведены в [журнале проверок](verification.ru.md).

## Выбор принтера и данные для проверки

Группа чтения принтера включает инвентарь AMS. Отдельная изменяющая группа `orca_printer_selection` выбирает бэкенд/устройство и синхронизирует поддерживаемое единственное сопло. Выбор устройства GUI общий для процесса Orca; подготовленные отправки всё равно используют явные ID устройства и повторно проверенные снимки.

Результаты нарезки содержат нативные оценки и ID использованных филаментов проекта. Подготовка возвращает привязанный к зафиксированной нарезке отчёт с отличиями от сохранённых пресетов и явно обозначенными базами сравнения переопределений. PNG различают расположение модели и завершённые траектории G-code (`scope: slice`). Навык рабочего процесса показывает отчёт перед одобрением либо после уже разрешённой отправки/отправки на виртуальную цель; он никогда не считает квитанцию передачи доказательством физической печати.

## Локальные рецепты

`recipes_contract.py` отвечает за версионированную валидацию, канонические идентичности RFC 8785 и переносимый JSON. `recipes_store.py` отвечает за неизменяемые ревизии SQLite, CAS-указатели актуальных ревизий, транзакции импорта, планы и долговечные квитанции применения. `recipes_native.py` отвечает за получение текущей совместимости, композицию и одно нативное изменение на план. Хранилище общее для клиентов; удерживаемая в течение жизни процесса блокировка ОС выявляет брошенные отправки, а проверки версии операции не позволяют устаревшим наблюдателям перезаписывать более новые квитанции. Ни один наблюдатель не повторяет нативные записи. Библиотеке рецептов не нужны изменения нативного форка. См. [контракт рецептов](contracts/recipes-v1/CONTRACT.ru.md).

## Репозиторий и установка

Нативный API, адаптер и навык находятся в одном форке OrcaSlicer. Python-исходники и тесты пакета находятся в `mcp/`; единственный источник навыка рабочего процесса — `skills/orca-mcp-control/` в корне репозитория. Навык распространяется отдельно от Python wheel и не становится зависимостью MCP во время выполнения. Английский `SKILL.md` остаётся единственным исполняемым источником навыка. Обычная сборка CMake не устанавливает Python и не зависит от пакета MCP.

`scripts/agent/install.sh` устанавливает исходный пакет или релизный wheel в пользовательское окружение uv tool. По умолчанию выводится универсальная конфигурация для любого stdio-совместимого MCP-клиента; параметры `--client codex` и `--client zcode` включают автоматическую настройку этих клиентов. Выбранные записи клиентов используют абсолютный путь установленного исполняемого файла; рабочее дерево и `.venv` разработки не требуются во время выполнения. Изменения конфигурации сохраняют остальные записи и создают резервные копии. Установщик не запускает Orca и не включает доступ агента или печать. Хранилище рецептов и нативные квитанции печати находятся вне установки. См. [установку](../../docs/agent/INSTALL.ru.md) и [распространение](../../docs/agent/DISTRIBUTION.ru.md).
