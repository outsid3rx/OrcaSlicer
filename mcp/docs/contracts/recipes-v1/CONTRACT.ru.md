# Контракт библиотеки рецептов Orca MCP v1

[English](CONTRACT.md) | **Русский**

Статус: **реализован в MCP 0.4.0**, 25 октября 2026. База создаётся сервером автоматически в приватном каталоге пользователя. Контракт библиотеки имеет версию 1 и не меняет wire protocol v1 / native API revision 3 Orca.

Библиотека — часть существующего Python MCP. Она хранит небольшие воспроизводимые наборы настроек, проверяет их против выбранного окна Orca и составляет одну нативную операцию применения. Локальное хранение, импорт и экспорт работают без аккаунта и собственного backend.

## 1. Граница первой версии

Рецепт содержит **явные присваивания настроек одного scope**, а не полный профиль принтера или изменяемую ссылку «используй latest». Несколько рецептов можно объединить для одного объекта/области. Один план применяется одним `settings.patch` с нативной валидацией и Undo. Для разных объектов или scopes создаются отдельные планы: общей атомарной транзакции между ними нет.

Поддерживаемые scopes: `process`, `plate`, `object`, `volume`, `height_range`, только в пределах ключей, разрешённых самим Orca. Например, рецепт области `object` можно применить к любому явно выбранному объекту, но нельзя автоматически превратить в рецепт `process`. Изменение scope требует новой редакции/форка и проверки контракта.

В v1 рецепт только задаёт `values`. Удаление overrides, сохранение профилей, импорт моделей, выбор устройств, нарезка и отправка печати остаются отдельными существующими операциями. Составных рецептов с исполняемыми зависимостями, скриптов и произвольных native-команд в формате нет. Итоговый план может объединять до 16 точных редакций.

Полноценный публичный каталог, автообновление из URL и текстовые коды обмена не входят в v1. Обязательный переносимый формат обмена — JSON-дамп. Поля автора и источника сохраняют происхождение для последующего каталога.

## 2. Рецепт, редакция и идентичность

Машинная схема: [recipe.schema.json](recipe.schema.json), определения: [contract.schema.json](contract.schema.json).

Запись состоит из `payload` и `sha256` его канонического содержимого.

| Поле payload | Значение |
|---|---|
| `format`, `format_version` | `orca.recipe`, `1` — версия переносимого формата |
| `recipe_id`, `revision` | Постоянный UUID рецепта и положительный номер неизменяемой редакции |
| `parent` | Полная ссылка на предыдущую редакцию этого ID; у первой редакции `null` |
| `derived_from` | Ссылка на исходную редакцию другого рецепта для форка; иначе `null` |
| `name`, `description`, `tags` | Название эффекта, пояснение и категории |
| `scope`, `values` | Одна область и `ключ → сериализованная строка Orca` |
| `native_contract` | Версия наблюдённого API и сигнатура каждого используемого ключа |
| `compatibility` | Явные ограничения по модели принтера, материалам, соплу, высоте слоя |
| `evidence` | Заявленные результаты физических проверок с условиями; не сертификат качества |
| `created_at`, `author`, `license`, `source_url` | Время редакции и необязательное происхождение |
| `deprecated`, `deprecation_note` | Предупреждение автора об устаревании этой редакции |

Полная ссылка `RevisionRef` всегда содержит `recipe_id`, `revision`, `sha256`. Применение никогда не принимает только название или `latest`. Поиск возвращает точную ссылку, текущий `head_version` и состояние архивирования.

У первой редакции `revision=1, parent=null`. Для N>1 родитель имеет тот же ID, номер N−1 и точный хеш; исходная редакция доступна в библиотеке или в импортируемом дампе. Циклическое происхождение запрещено. Неизвестный `derived_from` допустим как явно отмеченное неполное происхождение; он не является зависимостью и не загружается автоматически.

Редакция после записи неизменяема, включая описание и evidence. Исправление создаёт новую редакцию. Локальное изменение импортированного рецепта по умолчанию — `fork`: новый ID, редакция 1, `derived_from` указывает на точный исходник. Явный `revise` сохраняет ID и требует актуальный `expected_head_version`; авторство при этом не считается доказанным. Кроме того, head должен быть максимальной сохранённой редакцией этого ID. Если импорт уже сохранил более новые редакции без продвижения head, revise возвращает `head_not_latest`: нужно явно продвинуть head через import.prepare/commit либо создать fork. Занятые номера редакций не переиспользуются.

Одинаковые ID/номер/хеш при импорте — no-op. Одинаковые ID/номер при разных хешах — `identity_conflict`, без перезаписи и без частичного импорта. Совпадение названий не означает совпадение рецептов.

### Каноническое представление

`sha256` — нижний hex SHA-256 от UTF-8 представления **payload по RFC 8785 (JCS)**. Само поле `sha256`, отступы исходного файла, время импорта и локальные заметки в хеш не входят. Один и тот же payload обязан давать один хеш у всех клиентов.

Рецепты v1 используют только целые числа до 2^53−1, строки, bool, null, массивы и объекты. Десятичные измерения в compatibility — строки, например `"0.4"`; значения Orca также строки (`"4"`, `"30%"`, `"1"`). Это не разрешение произвольных строк: окончательный парсинг выполняет native API. Непарные UTF-16 surrogate, повторяющиеся JSON-ключи и нечисловые литералы NaN/Infinity отклоняются до хеширования. Нормализация текста Unicode не выполняется.

## 3. Совместимость и актуальность

`native_contract` — снимок при создании редакции: `protocol_version`, `api_revision`, `app_version`, `definitions`. Множество ключей definitions должно точно совпадать с values. Каждый элемент содержит native integer `type` и `sha256` значимой части определения.

Сигнатура ключа — JCS/SHA-256 объекта `{scope,key,type,min,max,enum_values,units}` из `settings.describe` выбранного scope. Отсутствующие min/max/units заменяются `null`, отсутствующий enum_values — `[]`; остальные поля не добавляются. Подписи исключают переводимые label/category. Уровень readonly/доступности проверяется отдельно по наличию ключа в writable-схеме. Наличие ключа в general config недостаточно.

Сервер запрашивает все нужные страницы схемы и значений, а не только первую страницу. Изменившийся номер API сам по себе не доказывает несовместимость или совместимость: проверяются протокол, необходимые методы, scope, типы и сигнатуры ключей.

Результат `check` разделяет:

- `compatible` — структурный контракт и объявленные ограничения подтверждены текущими данными;
- `migration_required` — ключ удалён, переименован либо его значимое определение изменилось;
- `incompatible` — известное условие точно нарушено;
- `unknown` — нужное условие нельзя проверить по доступным данным.

Проверяемые compatibility-ограничения относятся к текущему профилю/настройкам проекта. Физическая совместимость выбранного принтера и слотов остаётся проверкой `printing.prepare/submit`. Это разные проверки.

Для списка `filament_types` требуется, чтобы **все материалы, на которые распространяется применение**, входили в список. Нельзя использовать только первый слот или базовый материал объекта, если есть раскраска/поддержки. При неполном определении применимых материалов результат `unknown`, а не угадывание. Для сопел также проверяются все применимые диаметры. Диапазон layer_height включительный, min≤max, десятичные строки сравниваются как числа. Невыполнимое или неопределённое объявленное условие блокирует plan; флага force нет.

Отсутствие ограничения означает «автор не задал условие», а не «проверено для всего». Без положительного evidence, совпадающего с текущими проверяемыми условиями, создаётся предупреждение `unverified_recipe`. Неудачное испытание не снимает это предупреждение и добавляет `unsatisfactory_evidence`; неполные или отличающиеся условия — `evidence_environment_changed`. Положительный совпадающий импортированный отчёт всё равно помечается `reported_evidence`: он не становится доверенным свидетельством от самого MCP. Эти предупреждения требуют acknowledgement. Evidence из импортированного файла остаётся заявлением источника. Совпадение схем не доказывает одинаковое физическое поведение разных версий Orca.

Возраст записи сам по себе не делает её несовместимой. Выводятся дата и среда последней заявленной проверки, наличие новой локально известной редакции, deprecated и результат текущего check. Новая редакция предлагается для просмотра, но не заменяет старую автоматически. Ранее подготовленный план сохраняет точные ссылки на исходные редакции.

## 4. Композиция и план применения

[plan.schema.json](plan.schema.json), [requests.schema.json](requests.schema.json).

Вход plan: точные ссылки на 1–16 редакций, один `binding` и необязательные разрешения конфликтов. Binding содержит полную пару UUID окна, scope, актуальный plate_id, state_token и необходимые object_id/volume_id/height_range. Process меняет edited process для проекта, object/volume/range затрагивают все связанные instances; это явно показывается в impact/warnings.

Все рецепты должны иметь тот же scope, что binding. Для create/revise/fork draft.scope также обязан совпадать с capture_binding.scope. Одинаковое значение одного ключа объединяется с сохранением всех источников. Разные значения одного ключа — `composition_conflict`: порядок списка не выбирает победителя. Для продолжения клиент передаёт `resolutions=[{key,chosen_value}]`, где chosen_value — одна из конфликтующих строк. Лишнее, повторное или не относящееся к конфликту разрешение отклоняется.

Plan обязан:

1. Проверить хеши, доступность редакций и текущий native-контракт; собрать согласованный снимок исходных effective/own значений. state_token должен совпасть в начале и конце чтения всех страниц.
2. Показать diff, provenance и предупреждения. `before_own=null` означает наследование. Даже при равном effective значении создание override показывается как `changes_ownership=true`.
3. Преобразовать Binding через существующий scope_params: height_range становится native-полем `range`, target переносится в native params; UI-селекторы не угадываются. Зафиксировать один native `settings.patch` с исходными target/owner/state_token и отдельным UUID `native_request_id`. Секрет descriptor/auth в плане и базе отсутствует.
4. Проверить **≤256 ключей** и **≤65 536 байт полного JSON-RPC request**, включая method, id, target и state_token. Ограничение длины строки отдельно не заменяет проверку полного запроса.
5. Сохранить неизменяемый план с UUID, library_id, TTL 10 минут, отпечатком схемы и `plan_sha256`. Отпечаток плана — JCS/SHA-256 всех публичных полей Plan, кроме самого plan_sha256. После создания поля не меняются.

`schema_fingerprint` — JCS/SHA-256 объекта `{protocol_version:1,scope,definitions:[...]}`, где definitions — значимые объекты определений из раздела 3, отсортированные по key. app_version/api_revision в этот отпечаток не входят: они отдельные наблюдаемые метаданные.

Уровень валидации обязательно `schema_checked_native_validation_pending`. У текущего native API нет validate-only операции для полной effective-конфигурации. Plan проверяет форму, доступность, объявленные ограничения и известные значения enums/ranges, но **полная проверка кандидата и цепочек наследования выполняется нативным settings.patch при apply до записи**. План не вправе обещать эту проверку заранее.

`apply` получает plan_id, точный plan_sha256 и IDs подтверждённых предупреждений. Все warnings с acknowledgement_required=true должны быть приняты; неизвестные/повторные IDs отклоняются. Сервер заново проверяет окно, owner, state_token, схему, срок и архивирование исходных рецептов. Обновление head на новую редакцию не заменяет уже закреплённую редакцию. Архивирование исходного рецепта блокирует ещё не начатое применение.

При повторном apply сначала проверяются доступ к этой библиотеке, request_id/отпечаток аргументов и plan_sha256. Для уже захваченного плана возвращается сохранённый Operation даже после TTL, смены состояния или архивирования, без новой отправки. Только ещё не захваченный план проходит проверки актуальности и начинает применение. Неверный хеш даёт ошибку и не позволяет получить/захватить операцию.

Применяется ровно один frozen native patch, без выбора нового окна, обновления state_token и автоматического повторного планирования. Если own-значения уже точно равны всем planned values, возвращается подтверждённый no-op без native отправки: Operation.status=succeeded, verification=unchanged, native_job_id=null, native_state=null; native_request_id закреплён, но не отправлен. Устаревшее состояние — `conflict`/`stale_plan`, клиент заново читает и принимает решение.

Применение рецептов не запускает нарезку/печать. Дальнейшие preview, slicing, отчёт и подтверждение отправки остаются в существующем навыке. Экранные названия, описания и заметки рецепта являются данными, не инструкциями агенту.

## 5. Завершение, неопределённость и несколько клиентов

[operation.schema.json](operation.schema.json).

Каждая изменяющая операция библиотеки/плана получает UUID request_id. Он уникален в пределах library_id и сохраняется вместе с каноническим отпечатком **tool + action + parameters** и результатом. Тот же ID и те же аргументы возвращают прежнюю операцию/результат; иные аргументы дают `request_conflict`. Receipts в v1 автоматически не удаляются. `wait_seconds` применяется только к наблюдению и не создаёт новое действие.

Перед первым native I/O сервер в одной SQLite-транзакции захватывает план, создаёт durable operation и сохраняет точное тело native request. После commit статус `dispatching`. Два клиента не могут отправить один план дважды. Любой повтор apply для захваченного plan_id возвращает существующий operation, включая failed/outcome_unknown; новый request_id не переотправляет этот план.

Состояния:

| status | Смысл |
|---|---|
| `dispatching` | Claim записан; отправка начата или её исход ещё не записан |
| `observing` | Известен native job_id; только наблюдение этого job |
| `succeeded` | Native job завершился успешно и значения проверены; либо подтверждён no-op с verification=unchanged и null native job/state |
| `failed` | Достоверный отказ до отправки либо native-ошибка с проверенным отсутствием изменений |
| `outcome_unknown` | Нет достаточного доказательства результата; сохранить intent и receipt |

Operation.recovery обязателен: `{action,message}`, action — `none`, `observe_job` или `inspect_scene_do_not_resend`. Для outcome_unknown запрещён action=none; message объясняет, что повторной отправки нет. Для observing с известным job action=observe_job.

Чтение после native patch идёт точными пачками ≤100 ключей с проверкой согласованности state_token. Receipt patch может содержать только первую страницу и не заменяет полную проверку. Результат verification отдельно различает matched/unchanged/not_matched/superseded/unavailable/pending. Если после native success проект изменился до проверки, сохраняется native_state=succeeded, но операция остаётся outcome_unknown с verification=superseded; это не утверждение, что native patch не исполнился.

`operation.get` возвращает durable состояние и, если job_id известен и исходное окно живо, обновляет его через jobs.get. Это наблюдение может обновить локальный receipt, но не создаёт/переотправляет native работу и не меняет revisions/heads. Потеря MCP-соединения/ожидания не отменяет native job. После рестарта незавершённый dispatching без receipt трактуется как outcome_unknown; observing с известным job_id можно наблюдать дальше. Если native история уже потеряна, API не умеет доказать старый исход по request_id.

Повторная отправка native patch не является автоматическим recovery v1. Допустимое вручную организованное восстановление требует ровно исходного native_request_id и тела, с учётом ограниченной native retention; новое ID или свежий state_token не считаются восстановлением. Outcome_unknown нельзя «исправить» новым apply. Повторное намеренное применение требует чтения текущего состояния, нового плана и явного решения клиента. Автоматического Undo/rollback поверх возможных ручных правок нет.

SQLite использует WAL, foreign_keys=ON, synchronous=FULL и короткие write-транзакции с ограниченным busy timeout. Native I/O не выполняется внутри транзакции. CAS head_version предотвращает lost update и ABA при archive/unarchive. Изменения рецептов/heads увеличивают library_generation; создание планов и обновление receipts не меняют generation содержимого.

## 6. Dump и импорт

[dump.schema.json](dump.schema.json), [import-plan.schema.json](import-plan.schema.json).

Дамп содержит format/version, exported_at, recipes и heads с archived. Пустая библиотека экспортируется как пустые recipes/heads. Для selection=all include_archived по умолчанию true: полный экспорт включает все редакции и heads. При include_archived=false исключаются все редакции архивированных ID. Для явного списка selection флаг include_archived не принимается: выбранные точные редакции экспортируются независимо от archive с сохранением этого признака; выбранный экспорт включает выбранные редакции и транзитивное замыкание parent. Для выбранного экспорта head каждого экспортируемого ID — максимальная включённая редакция этого ID, archived копируется из библиотеки. Неразрешённый derived_from сохраняется как происхождение с предупреждением. Названия не являются ID.

Экспорт не добавляет базу SQLite, descriptor/auth, credentials, планы применения, operations, runtime window/object IDs и разрешения на печать. Пользовательские описания и прочий разрешённый текст переносится как есть: схема не является сканером секретов, которые автор мог сам вписать в заметку. Импорт файла сам по себе не применяет настройки к модели и не доказывает качество рецепта.

Ограничения v1: UTF-8 JSON ≤8 MiB, depth≤24, ≤4096 редакций, ≤1024 heads; отдельный payload ≤64 KiB, values≤256, строка значения≤4096 символов. Повторные JSON-ключи, неизвестные поля, неверные форматы, невалидные хеши/ссылки и недопустимая структура отклоняются до записи. Число экземпляров одной RecipeRef/ID+revision/heads должно быть уникальным. Множество ID heads должно точно совпадать с множеством ID recipes. Все размеры дополнительно проверяются по фактическим байтам, не только JSON Schema.

`dump_sha256` — JCS/SHA-256 всего объекта Dump, включая exported_at и порядок массивов; пробелы исходного JSON не влияют. Экспорт упорядочивает recipes по recipe_id/revision, heads по recipe_id.

`import.prepare` получает `parameters.dump` как **исходный JSON-текст**, чтобы обнаружить повторяющиеся ключи до разбора MCP-клиентом. Формат самого файла остаётся JSON-объектом Dump. Сервер валидирует и сохраняет ограниченную копию дампа, base_library_generation и план импорта с library_id и TTL 10 минут. import_plan_sha256 — JCS/SHA-256 всех публичных полей ImportPlan кроме самого import_plan_sha256; dump_sha256 и base_library_generation входят в него. Одинаковые записи отмечаются duplicates. Любой identity_conflict блокирует весь план без вставок. Существующие heads по умолчанию сохраняются; новые ID получают экспортированный head/archived. Явный advance_heads может только продвинуть существующий head по полной проверенной parent-цепочке; не откатывает и не снимает архивирование. Для архивированного рецепта требуется отдельное явное unarchive.

`import.commit` сверяет import_plan_sha256, TTL, generation и warnings и в одной транзакции вставляет все записи, обновляет выбранные heads и сохраняет receipt request_id. Изменившаяся библиотека даёт library_conflict; нужна новая подготовка импорта. Сам импорт не запускает URL, скрипты, плагины или фоновые обновления.

## 7. Обновления и миграции

Различаются три версии: SQLite `user_version`, переносимый `format_version`, наблюдённый native contract. Revision — четвёртый, независимый номер содержимого рецепта.

- **Хранилище:** предусмотренная кодом миграция версии SQLite выполняется с согласованной резервной копией через SQLite backup API, в эксклюзивном режиме обслуживания и транзакции. Неподдерживаемая более новая версия открывается с ошибкой без записей. При миграции не должно быть активных dispatching/observing операций; unknown receipts сохраняются. Каждый клиент проверяет storage version перед изменяющей фазой и не продолжает запись старым кодом после миграции.
- **Переносимый формат:** v1 принимает только format_version=1. Неизвестная будущая версия отклоняется. Когда появится поддерживаемый старый формат, преобразователь сначала сохраняет оригинал и создаёт проверяемую копию; он не переопределяет прежний ID/revision/hash другим содержимым.
- **Настройки Orca:** изменение сигнатур даёт migration_required. Известное проверенное правило может подготовить предлагаемые новые значения и объяснение; v1 не поставляет набор таких правил и не угадывает переименования. Подтверждённая адаптация сохраняется через revise/fork с новой редакцией/ID, parent/derived_from и заново захваченным контрактом. Подменять fingerprint внутри старого payload запрещено. Новая редакция с прежними values и новым контрактом допустима после явной проверки изменённых определений; это не автоматическое признание физической совместимости.
- **Обновление автором:** импортируется новая неизменяемая редакция. Просмотр differences и явное продвижение head отделены от адаптации API. Доказательства физической проверки не переносятся автоматически на изменённые параметры.

Файловый dump — обмен рецептами, не восстановление операционного журнала. Нельзя заменять им рабочую SQLite-базу и терять consumed intents. Возврат к резервной копии базы при возможной незавершённой отправке — обслуживание с сохранением/разбором журнала, а не автоматический повтор применения.

## 8. MCP-инструменты

Эти инструменты реализованы в MCP 0.4.0. Аргументы и action allowlists: requests.schema.json. Успешные ответы имеют `{contract_version:1,ok:true,data:{...}}`; ошибки — `{contract_version:1,ok:false,error:{kind,message,details}}`, MCP isError=true. Успех вызова apply/operation.get означает получение receipt: status=outcome_unknown всё равно имеет isError=true и явный recovery без resend.

| Tool | Actions | Основной результат data |
|---|---|---|
| `orca_recipes` | `describe` | library_id, library_generation, storage/format/contract versions, лимиты, доступные actions и request_schema; необязательные фильтры parameters.tool/action |
| | `list` | items с точными ref/head_version/archived, offset/limit/next_offset |
| | `get` | RecipeRecord, текущий head/ref/version/archived, заметка о происхождении |
| | `check` | список checks и conflicts, общий status; никаких изменений Orca |
| | `export` | Dump; при превышении лимитов — ошибка с предложением сузить selection |
| | `operation.get` | Operation; только наблюдение, без отправки patch |
| `orca_recipe_library` | `create` | RecipeRecord первой редакции + head_version=1 |
| | `revise`, `fork` | новая RecipeRecord + head_version; revise использует CAS, fork создаёт новый ID |
| | `archive` | head ref/head_version/archived после CAS |
| | `import.prepare` | ImportPlan, без изменения библиотеки рецептов |
| | `import.commit` | inserted/duplicates/head_changes и новая library_generation |
| `orca_recipe_apply` | `plan` | Plan либо composition/compatibility error; не меняет Orca |
| | `apply` | Operation; только одна frozen settings.patch |

Capture_binding для create/revise/fork получает действующие определения ключей для draft.scope и проверяет согласованность чтения. Он не меняет модель и не засчитывается как физическая валидация. В сохранённом recipe нет target/owner/state_token из capture. Поле evidence создаваемой/изменяемой редакции должно быть явно задано при наличии: без него сервер сохраняет пустой список, а не наследует подтверждение старой печати.

`orca_recipes` объявляется readOnlyHint=true, destructiveHint=false. Две остальные группы — readOnlyHint=false; библиотечная destructiveHint=false (редакции сохраняются, archive обратим), apply destructiveHint=true. Все openWorldHint=false: этот контракт не отправляет данные на принтеры или внешние каталоги. Import/export v1 принимают/возвращают JSON в tool payload, без произвольных файловых путей; локальные дампы читает/пишет клиент в пределах своих разрешений.

Создание receipt/плана требует durable write, даже если модель не изменяется, поэтому plan/import.prepare находятся в изменяющей группе. Конкретные результаты Plan/Operation/ImportPlan имеют отдельные схемы; общая response.schema.json задаёт только оболочку. Остальные результаты описаны этой таблицей и реализованы в схемах и сервисе с соблюдением основных инвариантов.

## 9. Хранение

Одна SQLite-библиотека текущего пользователя используется всеми MCP-клиентами. Путь по умолчанию macOS: `~/Library/Application Support/orca-slicer-mcp/recipes.sqlite3`; Linux: `$XDG_DATA_HOME/orca-slicer-mcp/recipes.sqlite3` или `~/.local/share/...`; Windows: `%LOCALAPPDATA%/orca-slicer-mcp/recipes.sqlite3`. Явный startup `--recipes-db` выбирает другую абсолютную базу, в том числе для изолированных тестов. Tool arguments не меняют путь базы.

Логические сущности: метаданные library_id/generation; неизменяемые revisions; mutable heads с head_version/archived; durable запросы/receipts; apply/import plans; apply operations. Payload хранятся в каноническом виде. База, WAL/SHM и backup приватны текущему пользователю. Ошибка доступа не разрешает незаметно создать другую пустую базу.

Ссылки в рецептах не содержат локальные пути к проектам и не требуют привязки к чату. Изменение window UUID, document epoch или scope owners делает старые bindings недействительными, но не удаляет библиотеку.

## 10. Примеры и критерии приёмки реализации

[examples/recipe.json](examples/recipe.json), [examples/library-dump.json](examples/library-dump.json), [examples/plan-request.json](examples/plan-request.json), [examples/import-request.json](examples/import-request.json), [examples/plan.json](examples/plan.json), [examples/apply-request.json](examples/apply-request.json).

Примеры содержат **синтетические native signatures**, обозначены fixture и не предназначены для применения. Это не проверенные рецепты отделяемых поддержек/мостов/разглаживания. Реальные рецепты требуют захвата действующего контракта и отдельных проверок печатью.

Проверяемые инварианты первой реализации:

1. Экспорт → импорт → экспорт сохраняет payload/ref/hash; foreign IDs и одинаковые названия не сливаются.
2. Одинаковые id/revision с другим hash отклоняют импорт целиком; ошибка/сбой не оставляет половину библиотеки.
3. Два клиента не теряют параллельную редакцию: CAS конфликтует, архивирование не создаёт ABA.
4. Смена ключа/type/range/enum/scope блокирует старый рецепт; значения сохраняются до явной адаптации.
5. Композиция одинаковых значений работает, конфликтующих — требует выбора; наследуемое равное значение не скрывает создание override.
6. План на другой UUID/plate/object/state/схему или после TTL не применяется. Смена head не меняет pinned payload.
7. Перед native I/O записан единственный intent. Сбой до/после admission и потеря reply не дают второй автоматический patch.
8. Проверяются все страницы и обе native границы 256 ключей/64 KiB. Успех не объявляется по одной странице receipt.
9. Storage migration сохраняет revisions/hashes/unknown intents и rollback backup; старый клиент после смены schema не пишет.
10. Импорт не выполняет содержимое описаний/URL, не выдаёт авторство за доверие и не переносит разрешение на печать.

Проверка JSON-схем подтверждает форму, примеры, хеши и негативные случаи. Отдельные тесты проверяют SQLite, конкуренцию, MCP stdio и потерянные ответы; изолированная GUI-проверка подтверждает применение на native API revision 3. Физическое качество печати этим не подтверждается.

В первой реализации доступна только инициализация storage 0 → 1 и явный backup через SQLite backup API; будущих миграций хранилища или семантики настроек пока нет. Неподдерживаемая версия отклоняется до записи. Точный material/model applicability текущий native API не раскрывает: объявленные ограничения этих типов дают compatibility_unknown и блокируют применение. Диаметр сопла читается из machine preset; высота слоя — из effective process.

Проверка проекта контракта из каталога MCP:

```sh
.venv/bin/python docs/contracts/recipes-v1/verify_contract.py
```

Нужны jsonschema и referencing из существующего окружения MCP. Проверка не подключается к Orca и ничего не применяет.
